# Incident: crash-looping backend serves 502 on every `/api/*` route

## Summary

A deploy shipped a backend container with no healthcheck. The container crash-looped, `web` (which
depended on it with `condition: service_started`, not `service_healthy`) came up anyway, and every
`/api/*` route returned 502 while the frontend shell kept serving. The deploy's own version-skew
check never ran, because the pipeline believed the deploy had already succeeded.

## Detection

**A human opening the site**, not monitoring — there was no monitoring. This incident is the
project's own stated reason the external monitor was built at all: "the only reason anyone found
out was a person opening the site" (`backend/src/scripts/external-monitor.ts:7–8`). Every
in-application signal that existed at the time — the masthead's sweep clock, `/admin/sources`,
`/status` — was served by the same process that was down, so none of them could report anything.

## What broke

`docker compose up -d --wait` treats a service with **no healthcheck** as ready the instant its
process starts. `backend` had no healthcheck while `web`, `db` and `minio` all did. `web` depended
on `backend` with `condition: service_started` rather than `service_healthy`, and
`restart: unless-stopped` kept restarting the dead `backend` container forever — a genuine crash
loop, not a single failed start. The deploy script's own version-skew check (steps 24/25/26 in
`deploy-aws-ssm.sh`) never ran, because by the time it would have run, the deploy already believed
it had succeeded. (`docs/STATUS.md:2441–2450`)

The frontend container came up and served its static shell, so the site *looked* reachable while
every `/api/*` route — `/api/health`, `/api/version`, `/api/meetings` — answered 502.

## Impact

Every backend-dependent page and API route was unreachable for the duration of the outage
(duration unknown in clock terms; the project's own account calls it "about four hours"). The
frontend shell still loaded, so a visitor would have seen a page that failed to populate rather
than a connection error. No data was lost — this was an availability fault, not a corruption or
data-loss one.

## Resolution

`backend` was given a healthcheck against its own `/api/health`, probed at **127.0.0.1, never
`localhost`** (a `localhost`→`::1` trap this project hit separately and documented in
`docs/STATUS.md:2351`). `web` now waits on `service_healthy` rather than `service_started`, and the
entrypoint names a migration failure explicitly instead of exiting silently.
`deploy/test-deploy-aws-ssm.sh` now asserts every service in the deployed compose file declares a
healthcheck (61 assertions, up from 53). (`docs/STATUS.md:2441–2450`)

## What changed as a result

- `backend`'s Docker healthcheck, added against `127.0.0.1/api/health`.
- `web`'s dependency condition changed from `service_started` to `service_healthy`.
- The entrypoint now names a migration failure rather than exiting silently.
- `deploy/test-deploy-aws-ssm.sh` gained an assertion that every deployed service declares a
  healthcheck.
- Indirectly: the external monitor (`backend/src/scripts/external-monitor.ts`), built afterward
  specifically because this incident showed every in-application health signal fails silently
  together with the process it depends on. See `docs/incidents/2026-08-15-disk-exhaustion.md` for
  the monitor's own blind spot, found later.
