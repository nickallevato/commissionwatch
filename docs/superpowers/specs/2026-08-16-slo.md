# A stated SLO for CommissionWatch — 2026-08-16

**What this is.** Roadmap item 6.6. As of 2026-08-16, `grep -rn -i "\bSLO\b|error budget|uptime
target|99\.9"` across `docs/`, `deploy/`, `README.md` and `.gitea/workflows/` returned zero hits
(`docs/superpowers/specs/2026-08-16-maturity-review.md` §1b) — nothing in this repository defines
what "up" means for this site, so nothing can say whether a past outage was a breach, and there is
no basis for deciding how much reliability work is enough. This spec is that definition.

**Who this is for and what it is not.** CommissionWatch is a volunteer-run civic transparency site
with **bus factor one** — `git shortlog -sne --all` returns one human beside the agent identity
(`docs/superpowers/specs/2026-08-16-maturity-review.md` §7a). A target promising 99.9% uptime would
be a lie on infrastructure with no on-call rotation and one person who can act on a page. **A lie in
an SLO is worse than no SLO** — it is the exact failure this project exists to catch in other
people's public claims, aimed at itself. Every target below is chosen to be something this project
can actually meet on the infrastructure it actually runs, and every target states how it is
measured with what already exists, or says plainly that nothing measures it yet.

---

## 1. Public site availability

**Target: 99.0% monthly availability of `GET /api/health` returning 200 with `database: connected`,
measured externally.** That is roughly 7.3 hours of allowed downtime per 30-day month — deliberately
loose for a single t4g.medium instance with no failover, no load balancer, and no second region.

**How it is measured with what already exists.** `backend/src/scripts/external-monitor.ts`'s
`evaluateHealth` check already probes exactly this, on a 15-minute tick
(`deploy/monitor-trigger.sh` driving `monitor.yml`'s `workflow_dispatch`, since scheduled triggers
do not fire on this Gitea instance — `docs/STATUS.md:1314–1323`). **What does not exist yet: nothing
aggregates those 15-minute readings into a monthly percentage.** The monitor reports a red Gitea run
on each failing tick; turning 96 ticks/day of pass/fail into a rolling 99.0% figure is unbuilt. Until
it is, this target is checkable by hand (count red monitor runs in a month, divide by total ticks)
but not published anywhere a reader can see it self-update.

**Why 99.0% and not higher.** The 2026-08-09 crash-loop incident
(`docs/incidents/2026-08-09-crash-loop-502.md`) was a real multi-hour total outage on this exact
infrastructure, caused by a healthcheck gap that is now fixed — but the next failure mode is
unknown by definition, and a single host with `restart: unless-stopped` as its only self-healing
mechanism cannot be promised more than a target that survives an occasional bad day.

## 2. Ingestion freshness

**Target: an enabled source with a stated `expected_interval_hours` sweeps successfully within 1.5×
that interval, at least 95% of the time it is measured.**

**How it is measured with what already exists.** `GET /api/ingestion/sources` already publishes
`adapter_key`, `enabled`, `expected_interval_hours`, and `last_success_at` per source
(`backend/src/services/ingestion/scheduler.ts:424`), and the external monitor's `evaluateSource`
already computes staleness from those fields against its own clock rather than trusting the feed's
self-report (`backend/src/scripts/external-monitor.ts:809–869`) — deliberately, because "the point
of an external monitor is not to ask the subject how it thinks it is doing." A disabled source is
skipped, and a source with no stated interval is skipped, both correctly: this target is about
whether an interval the project committed to is being met, not about inventing one for a source that
declares none.

**What does not exist yet:** the 95%-of-the-time framing above needs the same aggregation gap named
in §1 — the monitor reports pass/warn/fail per tick, and nothing rolls that into a percentage over
time. Today this is checkable per-tick (a single `fail` on `source:<adapter_key>` means this
target was missed *right now*) but not as a trailing rate.

**Why this matters more than uptime for a watchdog.** `SECURITY.md` already names *denial of
collection* as a vulnerability class — a site that stays up while quietly failing to sweep looks
identical to a healthy one on every check that only asks "is the site up," which is exactly the
blind spot `docs/incidents/2026-08-15-disk-exhaustion.md` demonstrates for deploys and that this
target exists to catch for ingestion specifically.

**Currently unenforceable, stated honestly:** both registered sources (`bozeman-granicus`,
`gallatin-civicplus`) are registered but their production enablement state changes by operator
decision (`docs/STATUS.md:2211`), and `mt_cers` is a third. This target applies only to whichever
sources are enabled at a given time — an SLO cannot promise freshness for a source nobody turned on.

## 3. Publication latency

**Target: none set, stated as a decision rather than an omission.**

`GET /api/metrics` already publishes `median_days_to_publish`
(`backend/src/services/metrics.ts:67,284`) — measured today, **28 days**, from a corpus of 215
meetings ingested and 1 published (`docs/superpowers/specs/2026-08-16-maturity-review.md` §7a,
probed against production 2026-08-16). That gap is not a latency defect to target down: the review
gate is a **person**, deliberately (`docs/roadmap.md` *Gaps* §1 — "this is not an argument for
weakening the gate; the gate is the project"), and a numeric latency target on a single-reviewer
process either becomes a pressure to approve faster than the record can be checked, or a number this
project will miss every month for a reason that is not a defect. Neither is honest.

**What is measured, and published, instead of a target:** the existing `median_days_to_publish`
figure, and `/status`'s disclosure of how much of the ingested record has actually been read
(`docs/STATUS.md:528–536`, the `PublicExtractionReading` discriminated union whose unmeasured branch
has no `unread_fraction` field at all). A reader can already see the real number. This section
states, as policy, that no target sits on top of it until Phase 7.1 (a second reviewer) changes what
"as fast as it can go" means for this project — see `docs/roadmap.md` Phase 7.1.

## What this SLO deliberately does not promise

- **No on-call rotation.** One operator. A pager for a team of one whose failure signal is already a
  red Gitea run and a Discord webhook (`backend/src/scripts/external-monitor.ts:1028–1054`) would be
  ceremony, not reliability — named as a deliberate scope decision in
  `docs/superpowers/specs/2026-08-16-maturity-review.md` §1's "Not gaps" and carried forward here.
- **No paging at night.** Nobody is woken by this project. The failed monitor run persists in
  Gitea's run list until the operator deals with it during hours they choose.
- **No guaranteed response time to a dispute.** `docs/STATUS.md:1282–1288` records that this project
  already removed four unenforced clocks from its own Methodology page — "2 business days," "10
  business days," "24 hours," "3 business days" — none of which anything in the codebase measured,
  tracked, or alerted on, and replaced them with a table of what is actually guaranteed and by what
  mechanism. This SLO does not reintroduce that pattern for disputes, corrections, or anything else.
  If a response-time commitment is made in the future, it needs the same enforcement discipline —
  measured by something, not asserted in prose.
- **No error budget policy yet.** An SLO without an error budget is a target with no consequence
  attached to missing it. Until the aggregation gap named in §§1–2 is closed — turning per-tick
  monitor readings into a rolling percentage — there is no live number to spend a budget against,
  so no error-budget policy is stated here. Adding one before the underlying measurement exists
  would be inventing a second number nobody can check, which is exactly the failure mode this
  project exists to catch in others.

## What would make this SLO enforceable rather than aspirational

In order of what unblocks the most:

1. **Aggregate the external monitor's per-tick pass/fail into a rolling percentage**, per check,
   over a trailing 30 days. This single piece of work makes §1 and §2 checkable as stated rather
   than only checkable per-tick by hand.
2. **Publish the resulting percentages somewhere a reader can see them** — `/status` already states
   the ingestion-read fraction in the reader's own words; the same discipline applies here.
3. **Revisit §3 once Phase 7.1 (a second reviewer) lands.** A latency target is honest only once
   "as fast as the record can be checked" is no longer bounded by a single person's calendar.
