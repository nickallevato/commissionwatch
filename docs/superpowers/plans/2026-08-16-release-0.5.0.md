## Standing rules

1. **One dev subagent at a time.** The main loop plans, verifies, commits, keeps loop health, and
   answers the agent via `SendMessage`. If the agent is still running at a tick, do not dispatch a
   second one — take a main-loop-only task instead, or do nothing.
2. **The subagent never runs a git write command.** No `add`, `commit`, `checkout`, `stash`,
   `reset`, `push`. Read-only git is fine. The main loop commits.
3. **`git add -A` is banned while an agent is running.** It swept 1,083 lines of an in-progress
   feature into an unrelated `docs:` commit last loop. Stage explicit paths.
4. **Verify with real command output, never with an agent's claim.** Backend and frontend
   `typecheck` + `test` + `build` before every commit. **`blocked` is not `pass`.**
5. **Never run the backend suite from the main loop while the agent may be running it** — one test
   database, and concurrent runs collide.
6. **A guard that has never been seen to fail is not known to work.** Every new invariant test gets
   mutation-verified in both directions, and the mutation output goes in the commit message.
7. **Push to `origin` (Gitea), not `github` (the mirror).** Read the printed sha range, not the exit
   code.
8. **Nothing new publishes prose about a named person without a flag defaulting to off and the
   review queue in front of it.** The walls get no flag — see the feature-registry design.

## Tasks, in order

### G1 — the test suite's own reliability  *(small, first, unblocks trust in every later gate)*

- [x] **G1a** `backend/test/prerender.test.ts` drives `consumer.tick()` from a **null cursor**, and
      `tick` reads `limit(200)` in `(updated_at, id)` order. Once `events` holds >200 rows older than
      the fixtures, the tick spends its batch elsewhere and the suite fails — **including on "a
      withdrawn meeting kept its prerendered page"**, the worst failure this system can produce.
      Seed a cursor positioned just before the fixtures instead of starting from null.
      **Acceptance:** the test fails on `main` with ≥201 orphaned older events present, and passes
      with the fix under the same conditions. Demonstrate both.
      *(Was F9b.)*

### G2 — the silent deploy failure  *(the finding the last loop ended on)*

- [ ] **G2a** Nothing alerted when the release stopped deploying, because the external monitor asks
      whether the **site** is up and it is. Add a **release-drift check**: compare
      `/api/version`'s sha against the head of `origin/main`, and report a drift older than a
      threshold as a failure. This needs no AWS credentials and no host access.
      **Where:** extend the existing monitor rather than adding a second one — see
      `deploy/monitor-trigger.sh` and the monitor service in `backend/src/services/`. Read the
      existing check shape first; do not invent a parallel mechanism.
      **Acceptance:** a test in which the reported sha differs from the expected head produces a
      failing check with both shas in the message, and one in which they match produces a pass.
      **Guard:** the check must distinguish *"the shas differ"* from *"the version endpoint could not
      be read"*. Those are different events and reporting them the same way is the exact error
      pattern this project keeps finding.

### G3 — the archive with no data in it

- [ ] **G3a** `dated_export_archive` shipped with a writer (`npm run export:snapshot`) that **nothing
      ever calls**, so the feature serves 404 for every date. Give it a scheduled path: a snapshot
      stage that runs on the existing Postgres `SKIP LOCKED` queue / scheduler rather than a new
      timer, gated behind the existing `dated_export_archive` flag, **default off**.
      **Acceptance:** with the flag off, no snapshot row is written and the scheduler records that
      it was skipped rather than silently doing nothing. With it on, one run writes exactly one
      snapshot per day and a second run the same day is a no-op rather than a duplicate.
      **Read first:** `backend/src/services/export/archive.ts`, `backend/src/scripts/export-snapshot.ts`,
      and the ingestion scheduler — reuse its idioms.
