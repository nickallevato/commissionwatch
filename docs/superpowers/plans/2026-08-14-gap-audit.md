# Gap audit — 2026-08-14

> Found by reading the code after the design phase, not by brainstorming. Every item below cites the
> file and line that proves it. Ordered by what would hurt most if left alone.
>
> The ten specs cover what the roadmap decided to build. This covers what is already there and
> wrong, plus the features nobody has proposed yet.

---

## A. Confirmed defects

### A0. Minutes are stored and never indexed, so the substance of the record is not searchable

Found by the transcripts probe and verified directly. `services/ingestion/handlers.ts:653-658`:

```ts
if (ctx.target.documentType !== undefined && ctx.target.documentType !== "agenda") {
  // Minutes, packets and attachments are stored and left for the parsers
  // that understand them. Extracting agenda items from minutes would
  // manufacture an agenda that was never published.
  return { counts: { parse_not_agenda: 1 } };
}
```

That returns **before** `recordArtifactText` at line 680. So `artifact_texts` — the table
`services/search.ts` searches for document body text — contains agendas only. **Minutes, packets and
every attachment are fetched, stored, content-addressed, and never indexed.**

The comment is right about what it defends: extracting agenda items from minutes would manufacture
an agenda that was never published. It is wrong about the scope of the return. The code itself makes
exactly this distinction twenty lines later, in a comment at line 677:

> "Held before the items are extracted, because the two answer different questions and the second one
> failing must not lose the first. **A document whose items cannot be read is still searchable by its
> text.**"

That principle is stated, implemented, and then bypassed for every document class it matters most
for. Minutes are the substance of the record — they are what the entire extraction pipeline reads to
produce claims — and a reader searching for a phrase said at a meeting gets nothing.

Fix: index the text for every parsed document, then branch on `documentType` for item extraction
only. It is a small restructure, it is a prerequisite for the transcripts spec (which needs the same
path for VTT), and **it is probably a larger week-one corpus win than transcripts themselves**.

Relates to B1 below: search that covers the wrong corpus and search that omits claims are the same
problem seen from two ends.

### A1. `/api/health` reports `status: "ok"` while the database is down

`backend/src/routes/health.ts:18-40`. The handler catches the `SELECT 1` failure, sets
`database: "disconnected"` — and then returns `status: "ok"` unconditionally. There is no path by
which `status` is anything but `"ok"`.

So a load balancer, an uptime monitor, or a container healthcheck watching the obvious field sees
green throughout a total database outage. **This project has had a production outage** (`STATUS.md`,
2026-08-09) and is about to have an external monitor installed against exactly this endpoint. The
monitor would have reported healthy.

Also missing from the check: object storage (MinIO holds every artifact — the corpus is unreadable
without it) and the migration version (a deployed image running against an un-migrated database is
the crash-loop shape this project already hit).

Fix: `status` derives from the checks. `503` when a hard dependency is down, so an HTTP-status-based
monitor works without parsing the body. Keep a separate liveness endpoint that answers 200 whenever
the process is up, because restarting a process that is merely waiting on a database makes an outage
longer, not shorter.

**This one should be fixed before the external-monitor cron is installed**, or the cron is
decoration.

### A2. Nothing rate-limits any public endpoint except the dispute route

`FixedWindowLimiter` (`services/rate-limit.ts`) has exactly one consumer: `services/disputes.ts:79`.
Nothing else. Not `/api/data`'s bulk exports, not `/search` — which runs four full-text queries
across a four-table join per request — not `/api/meetings`, nothing.

**The Caddy IP allowlist is currently the rate limiter.** Taking that allowlist down is on the
operator's task list and is otherwise ready to happen; the security defect that argued for keeping
it up was closed on 2026-08-14. Removing it without this exposes the most expensive query on the
site to anyone.

This compounds with the design phase: the delivery spec's `/feed.xml?q=…` accepts arbitrary query
text by design, and the server-rendering spec already requires 429/`Retry-After`. Do it once,
centrally, and cover the existing routes at the same time — not per new feature.

### A3. `GET /api/meetings/:id/rundown` is a public route that can only ever 404

`routes/meetings.ts:122` reads `rundown_sheets`. That table's only writer died with the `agents/`
deletion, so the query always returns nothing and the route always answers:

> `"Rundown not yet generated for this meeting"`

"Not yet" is a promise. The route states, to every caller, that something is coming which nothing in
the codebase produces.

The design phase already had a view on the table: the published-claim spec recommends retiring
`rundown_sheets`, because the claim card is what it was reaching for. Retire the table and the
route together, or — if the rundown concept is wanted — say so and give it a writer. What it must
not stay is a public endpoint making a false statement about the future.

### A4. `services/embeddings.ts` is dead code from withdrawn work

Zero importers — no file in `src/` or `test/` imports it. `storeChunks` inserts rows with
`embedding: null`, and the comment says "Actual embedding generation will be implemented in Phase 3".

Phase 3 is not coming: `services/search.ts:8` records that **the embedding work was withdrawn**
(archive-salvage spec § A3) and that full-text search deliberately replaced it — "No vendor, no API
key, no per-call cost, no dimension decision." That was the right call.

So this is not an unfinished feature, it is a leftover, and it carries two costs. `document_embeddings`
and the pgvector extension are declared, deployed and unused, which makes the stack table in
`CLAUDE.md` misleading in the same way `docs/spec/architecture.md` was wrong for months. And the
file imports `../config/database` as a module singleton rather than taking a `Knex`, unlike every
other service — a pattern nobody should copy from it.

Delete the service. Decide deliberately whether to drop the table and the extension, since dropping
pgvector is a deployment change and semantic search over the claim corpus is a plausible future
want. Recommendation: delete the service now, keep the extension, and note in the stack table that
it is reserved and unused rather than active.

### A5. The SPA is served with no security headers, and an artifact viewer is about to render untrusted bytes

`app.ts:72` applies `helmet()` to the API. `frontend/nginx.conf` sets one header, a `Cache-Control`
at line 47. No `Content-Security-Policy`, no `X-Frame-Options`, no `Referrer-Policy`, no HSTS at
this layer.

That is tolerable for a site rendering its own JSON. It stops being tolerable with two things the
design phase just specced:

- **`/source/{sha256}`** — the artifact viewer, which renders text extracted from third-party PDFs
  and HTML. `services/search.ts:24` already identified this hazard in its own domain and solved it
  properly: `ts_headline` is given control characters rather than `<b>`, explicitly because
  "returning it as markup for the frontend to inject would be an XSS hole opened for a typographic
  effect." The artifact viewer must inherit that discipline and be backed by a CSP, not only by
  careful rendering.
- **The map**, whose spec already forbids third-party tile hosts. A CSP is how that becomes
  enforced rather than intended.

`Referrer-Policy` matters on its own: a reader following a citation from a page about a named
official should not send that page's URL to the county's web server.

### A6. There is no privacy or data-handling page

No page under `frontend/src/pages/` is named for privacy, terms, or data handling. The site has
`/methodology`, `/data-license` and `/public-records`, which describe conduct toward *sources* —
nothing describes conduct toward *readers and disputants*.

`record_disputes` already stores a `contact` field that a member of the public typed. The
notification spec now adds outbound transactional mail to that contact. The delivery spec has
subscriber email behind it.

The good news is that the honest version of this page is unusually short and unusually strong,
because the answers are already true in code: no analytics, no tracking pixels, no IP addresses
stored on disputes (`services/disputes.ts` header, property 5), no click tracking on mail
(notification spec), no query logging on the feed (delivery spec §2), and donor addresses actively
*deleted* in migrations 043 and 051. That is a better privacy posture than almost any civic site
has, and it currently goes unstated.

Under a mandate of "follow the law, push the tech", this is the paperwork half, and the regions
module is the precedent: the constraint becomes data the code reads, not prose nobody enforces. The
page should be generated from what the code actually does wherever possible.

## B. Coverage gaps in things that exist

### B1. Search does not cover findings, and will not cover claims

`services/search.ts` searches four kinds: agenda items, meetings, members, and `artifact_texts`.
Not `anomaly_flags`. Not `minute_claims`.

So the Findings page has no search, and the claim corpus — the thing the entire extraction pipeline
exists to produce — will be unsearchable on the day it ships. A reader who wants "every time this
official voted against a rezone" cannot ask.

Adding a fifth and sixth branch is cheap and the file's structure was chosen to make it cheap: four
separate queries merged in ordinary code, "testable without a database", each a plain indexed
lookup. The wall comes with it — `whereFindingPublic` and the new `whereClaimPublic` exist and must
be used rather than retyped.

**Sequence it with the claim pipeline, not after.** Search added later is search that gets a
re-typed publication predicate.

### B2. The operator audit trail is partial

`operator_actions` (migration 071) has exactly one writer: `services/pressroom/sources.ts:414`. So
source management is audited and nothing else is — not review decisions, not extraction runs, not
policy changes, not publishing.

Some of that is by design: `record_corrections` is deliberately the one audit log for record
changes, and `services/review/queue.ts` appends every decision there. But that leaves two logs with
an unstated boundary, and the honest question is which one answers "what did the operator do on
Tuesday". Today, neither does completely.

Decide the boundary and write it down: `record_corrections` for anything that changes a record,
`operator_actions` for anything else an operator did that has consequences. Then make the second one
actually cover them. With one operator this is low-stakes; with two, or with any external review of
a contested decision, it is the whole ballgame.

### B3. Nothing states a retention or deletion policy

No document says how long anything is kept or what gets deleted. Relevant now, because:

- `record_disputes` holds a member of the public's contact details indefinitely.
- `http_cache` and `artifacts` grow without bound, and the receipt in the delivery spec adds a
  weekly snapshot forever.
- The event spine spec explicitly says `events` is never deleted — correct for an audit record, and
  it should be a stated policy rather than a line in one spec.

The right answer is probably "the public record is kept permanently, personal data is not", with a
stated window for dispute contacts after resolution. It is a short document and it belongs with A6.

## C. Features nobody has proposed

Ordered by value per unit of work. I would build C1 and C2; C3 and C4 are worth a decision, not
necessarily a build.

### C1. Agenda-to-outcome tracking — "what happened to this?"

The project ingests agendas and minutes and detects agenda *diffs* (`services/agenda-diff.ts`). What
it cannot answer is the question every resident actually asks: **an item appeared on an agenda —
what happened to it?**

Items get tabled, continued, withdrawn, re-noticed under a different number, and quietly never
return. That last case is the one nobody can see, and it is invisible precisely *because* nothing
happened. A transparency project that only records events cannot report a non-event.

This needs a `matters` concept: a durable identity for a subject of decision, linked across the
agenda items and vote events that touch it, with a state (`pending`, `decided`, `withdrawn`,
`dormant`). Then `/matters/{id}` is a timeline, "tabled four times over eleven months" becomes a
detectable finding, and — with the map — a parcel page can show a rezone's whole history rather than
a scatter of disconnected meetings.

It composes with almost everything else specced: `vote_events` supplies the outcomes, the geography
layer supplies the location, the feed supplies "tell me when this moves", and it is the object a
reader most wants a stable URL for.

### C2. A public metrics page — the project's own numbers

`/status` reports ingestion health. Nothing reports the shape of the corpus: meetings by year,
extraction coverage, claims held versus approved, median time from meeting to publication, disputes
received and upheld, sources by posture.

Two reasons this is worth more than it sounds. It makes the project's own performance auditable by
the same standard it applies to others, which is the strongest credibility move available to a
watchdog. And **median time-from-meeting-to-published and the held-versus-approved ratio are the two
numbers that would have exposed the current state early** — "1 meeting, 0 votes, 0 findings" was
true for a while before anyone framed it as the binding constraint.

Cheap: the queries exist, and the receipt in the delivery spec computes most of them already.

### C3. Multi-jurisdiction onboarding as a measured path

The stated ambition is that a third jurisdiction is configuration rather than a rewrite. Nothing
tests that claim. `jurisdiction_access_policy` and the adapter contract suites are the right
foundations, and the gap is that nobody has tried to add a fourth source end-to-end and counted the
code changes.

Recommendation: not a feature, a **test**. Pick a nearby Montana jurisdiction, run the onboarding,
and record what had to change. If the answer is "a config row and an adapter", the claim is true and
worth saying publicly. If it is more, that is the roadmap.

### C4. A "what changed" diff on the record itself

`document_versions` exists and `agenda-diff.ts` computes diffs. What is missing is the reader-facing
version: **when minutes are reissued, what changed?** A county quietly amending a published record
is exactly the event this project exists to catch, and the data to catch it is already stored —
content-addressed artifacts make it a sha comparison.

Small, high-signal, and it makes the case for content-addressing legible to a reader in one screen.

## What I would do first

0. **A0** (minutes are not indexed) — the highest-value line-count-to-corpus ratio available, and a
   prerequisite for the transcripts spec.
1. **A1** (health check lies) — before the external-monitor cron is installed.
2. **A2** (no rate limiting) — before the Caddy allowlist comes down. These two are ordering
   constraints on operator tasks that are already queued, which is why they lead.
3. **A3 + A4** (rundown route, dead embeddings service) — deletions, an afternoon, and they stop two
   pieces of the codebase from lying about themselves.
4. **A6 + B3** (privacy page, retention) — before transactional mail ships, since that is the point
   at which we start writing to members of the public.
5. **A5** (CSP) — with the artifact viewer, because that is the page that renders untrusted bytes.
6. **B1** (search over claims and findings) — with the claim pipeline, not after.
7. **C1** (matters) — the largest genuinely new idea here, and the one that turns a pile of meetings
   into a story a reader can follow.
