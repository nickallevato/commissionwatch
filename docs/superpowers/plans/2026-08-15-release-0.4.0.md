## How this file is used

This is the loop's memory. The orchestrator reads it at the top of every tick and the dev subagent
is pointed at exactly one task from it. Update the checkbox **and** the notes line the moment a task
lands — a tick that loses context must be able to resume from this file alone.

States: `[ ]` not started · `[~]` in progress · `[x]` landed and committed · `[!]` blocked, reason
stated · `[-]` dropped, reason stated.

## Standing rules for every task

- `cd backend && npm run typecheck && npm test && npm run build`, and the frontend equivalent, before
  any commit. Backend tests need `docker compose up -d db`.
- **Register every new test file in `backend/package.json`'s explicit test list.** The list is
  explicit; a new file not added to it runs nowhere and reads as passing. This has bitten before.
- No `any`, no `@ts-ignore`, no cast to quiet the compiler, no skipped or deleted test.
- The database schema is the source of truth for types.
- Never add `.github/workflows/`. CI is Gitea Actions.
- New migrations append: next free number is **104**. Do not fill the gaps at 096 and 101 — they are
  archive-salvage artifacts and reusing them makes two lineages collide.
- No CHECK constraint spanning a nullable column. See `098_null_safe_check_constraints.ts`.
- Any feature that changes what a stranger can read ships **behind a registry flag, default off**.
- The dev subagent does not run `git add`/`commit`/`checkout`/`stash`/`reset`. The orchestrator
  commits. Read-only git is fine.

## F1 — Feature registry and the admin console  ⟵ START HERE, everything else depends on it

**F1a–F1c landed.** 1869/1869 backend tests pass, typecheck and build clean. Decisions the spec did
not settle, recorded here because F1d–F1i depend on them:
- `mcp_server` is `risk: 'publishes'`, not `low`. It exposes no unpublished record, only a new
  audience — but reachability is what a risk grade is for, and the conservative grade costs nothing.
- **Writing `false` where no row exists is not a no-op.** Off-by-decision and off-by-default are
  different facts, and the former is the write that overrides a legacy env var still saying on.
  `enabled_from` is null there, which is what the nullable column is for.
- The pre-load gate is *"is this key in the cache"*, not `loadedAt !== null` — a key is in the map
  only if this process read it from the database, so a post-commit `setFlag` reflects immediately
  without a second flag.
- `EVENT_DRAIN_ENABLED=false` reports `source: 'default'`, not `'legacy-env'`. Same value, and
  honest: nothing enabled it.
- The process singleton is **settable, not constructed in the service** — importing `config/database`
  there would open a pool on any flag check, including in tests with no database. `src/index.ts`
  installs it, which is F1d/F1e work.

## F2 — The extraction repetition loop

The highest-leverage build in the backlog. 20.8% of chunks unread, **100% `truncated-reply`**, and
the cause is legible in yesterday's numbers: truncating documents emitted 86–127 "claims" from
3.5k–6.5k characters of a record containing a handful of votes, with rejection tallies
`unknown-action: 103` and `not-an-official: 113`. That is a repetition loop. Chunk splitting was
correctly refused — splitting a chunk that loops gives two chunks that loop.

- [x] **F2a** Reproduce it. `npm run extraction:distribution` to re-read the ledger, then run the
      real extractor over one known-truncating stored document and **capture the raw reply**. Do not
      design against the tally; read the bytes and find out what the repetition actually looks like.
- [ ] **F2b** Write the finding into the plan notes below before changing anything. If the repetition
      is the model restating one vote in n phrasings, the fix is a stop condition and de-duplication.
      If it is the model enumerating every name in a roster block, the fix is upstream in the prompt's
      framing of the chunk. **These have different fixes and the bytes decide which.**
- [ ] **F2c** Implement the fix. Candidates, in the order the evidence should be tested against:
      an early-stop on repeated claim signatures; de-duplication by `(action, official, locator)`
      before the verifier ever sees them; a prompt that names the expected order of magnitude. Not a
      token-ceiling raise — it has already been raised twice on the other reading and the error text
      no longer advises it.
- [ ] **F2d** Re-measure over the same corpus and record the new distribution. A fix that does not
      move the 20.8% is not a fix, and reporting it as one is the failure this project refuses.
- [ ] **F2e** If and only if the measured unread share is materially down, make extraction
      schedulable as a queue stage behind flag `scheduled_extraction` (add to the manifest,
      default off). A batch runner is a queue stage, not a loop in a route.

**Notes — F2a is done and the bytes decide the fix.** It is the **first** case: the model restates
claims it has already emitted, **verbatim**. It is not enumerating a roster.

Four stored documents run through the real path (MinIO → `extractPdfText` → `chunkText` → one
`client.complete` with the real system prompt), nothing written to the database:

| reply | chars | objects | distinct | most repeated | loop starts |
|---|---|---|---|---|---|
| `571a3e69` | 3,070 | 13 | 13 | 1 | clean |
| `61ce386a` | 4,639 | 16 | 16 | 1 | clean |
| `6f186a74` | 34,531 | 99 | **4** | **33** | index 4 |
| `b1361741` | 31,498 | 95 | **4** | **92** | index 4 |

`b1361741` emits one object 92 times and is cut mid-string. `6f186a74` is a clean **3-cycle** —
`0 1 2 3 0 3 2 0 3 2 0 3 2 …` — four distinct claims, three of them cycling 33/32/33 times.

**In both cases the genuine claims come first and the loop starts at index 4.** That reframes the
headline number: the chunk was *read*, and the reply was cut off after the distinct content had
already been emitted. The 20.8% "unread" counts those chunks as lost when the evidence says nothing
was lost in these two. **The measure may be overstating the problem, and a fix that only makes the
number go down without establishing that is worthless.** F2d must therefore show, per truncated
chunk, whether any distinct claim fell after the cut — not merely that the percentage moved.

Three further findings:
1. **Stochastic, not a property of the document.** `61ce386a` truncated twice in the ledger (88 and
   105 claims) and came back clean at 16 claims on this run. There is no bad-document list to build;
   the guard has to be a runtime one.
2. **The raised ceiling is what the loop spends.** `DEFAULT_MAX_TOKENS = 8000`; a looping reply
   reaches 31–35k characters against 3–5k for a clean one — roughly 7× the tokens and ~65s against
   ~11–18s, to produce four distinct facts.
3. **The rejection tallies are a separate problem and would survive this fix** — see F2g.

## F2g — the office gate rejects a whole body's minutes  (filed from F2a, not scheduled)

Corpus-wide rejections: `not-an-official 418`, `unknown-action 204`, `quote-not-found 84`,
`subject-not-in-quote 5`. The clean replies say why. These documents are a **Weed District board**
whose minutes print bare first names — "Larry", "Kelsy", "Bernie", "Zach", "John" — with no office,
while the prompt demands Mayor/Deputy Mayor/Commissioner and `verify.ts` rejects the rest.
`unknown-action` is invented verbs outside `CLAIM_ACTIONS`: `asked`, `informed`, `mentions`, `said`,
`suggested`, `to pass along`, `updated`.

De-duplicating a 92× repeat removes 91 rejections and does not make **one** more claim publishable.

**Not scheduled, and not a quick fix.** The office gate is deliberate — it is what lets extraction
run before a sourced roster exists, and loosening it to accept a bare first name is exactly the
change that would put an unverifiable person's name on a page. It needs the roster (blocked on a
records request) or a spec of its own. Do not treat it as cleanup.
